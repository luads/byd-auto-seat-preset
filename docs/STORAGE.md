# Preset storage contract

The authoritative schema-1 document contains presets and two distinct favourite IDs. It preserves names, supported coordinate source/format, numeric axes and optional capture time. It excludes permissions, developer/startup/update preferences, keys, previous results and movement requests. Imports are bounded to 64 KiB, 2–32 unique presets, 48-character names and 1–16 finite named coordinates. Invalid types, missing metadata, orphan favourites, duplicate IDs, negative timestamps, trailing data and unsupported schemas are rejected before writing. Valid geometry from another adapter can be retained, but cannot recall through an incompatible adapter. Simulation additionally requires exactly one integral demo-axis coordinate in 0–100.

App-private presets.json is written with Android AtomicFile, explicit sync and readback verification. presets.previous.json holds the prior successful snapshot and is written before replacing the primary. A process-wide lock serializes app, widget and panel access. The AtomicFile API does not provide locking itself: [Android API reference](https://developer.android.com/reference/android/util/AtomicFile).

Existing preference data is validated on read. The first successful edit/import stores the atomic document. A preferences mirror remains for existing diagnostics but is not authoritative after migration. Runtime preferences remain independent and are not changed by import.

If the primary is corrupt or absent while a previous snapshot exists, display the previous snapshot with a recovery notice. Recall and normal edits are blocked until explicit confirmation. If neither snapshot parses, display unsaved default cards with a damage warning, block normal saves and allow confirmed validated import. Raw damaged documents are not automatically replaced by a read. Import may explicitly replace damaged data; it never calls Vehicle. A previous snapshot can omit the most recent successful edit, so recovery needs owner review.

Capture rechecks eligibility and reads the current position when Save is confirmed, rather than saving coordinates read before the dialog. A failed capture or save leaves the previous successful document. Export/import cancellation leaves storage unchanged. No queued movement exists.

JVM regression tests cover legacy migration, metadata/name/favourite roundtrip, malformed and oversized documents, type/schema rejection, duplicate/orphan data, incompatible simulation geometry, interrupted persistence, previous-version recovery, both snapshots damaged and invalid import. Platform AtomicFile behavior and Android file-provider integration are checked separately on the Android 11 emulator. Real power-loss behavior, coordinate semantics and physical movement remain untested.
